07 · The tempting shortcut

Keep refresh tokens
out of SQLite

Anna wants reminders on each customer's Google Calendar. The shortcut is a google_refresh_token column. Instead, Auth0 Token Vault holds the Google tokens — your app only ever sees a short-lived access token.

ConcernDIY: token column in SQLiteAuth0 Token Vault
Where the Google refresh token livesIn your DB Next to customer data in data/anna-grooming.dbIn Auth0 Never written to this app's process or disk
Encryption, rotation & revocationDIY Yours to build, audit and keep patchedManaged Auth0 stores and refreshes it for you
If the database leaksHigh risk Every connected calendar is exposedLow risk Only calendar_event_id / calendar_event_link
Code you writeLots OAuth dance + refresh logic + storageOne call getAccessTokenForConnection({ connection: "google-oauth2" })

08 · Token Vault + Connected Accounts

Connect once. Tokens on tap.

The Connect button
/auth/connect?connection=google-oauth2

Mounted by enableConnectAccountEndpoint: true

1
Connect Google Calendar

The customer clicks Connect. The SDK routes them to /auth/connect asking for offline_access + calendar.events.

2
My Account API

/auth/connect talks to /me/v1/connected-accounts on your tenant, then hands off to Google's consent screen.

3
Token Vault keeps it

Google's refresh token lands in Auth0 Token Vault, linked to the customer — never in SQLite.

4
Book → fresh token

getAccessTokenForConnection returns a short-lived Google token, and the reminder lands on the customer's primary calendar.

The real Connect URL · built by getGoogleConnectUrl() in lib/config.ts
/auth/connect?connection=google-oauth2&returnTo=/&scopes=openid&scopes=profile&scopes=email&scopes=offline_access&scopes=https://www.googleapis.com/auth/calendar.events

11 · Secure MCP with OAuth 2.1

Agents book as the customer

No shared static API key. The agent is an OAuth 2.1 client that registers itself with Auth0, the customer consents, and every tool call is scoped to the sub on a verified JWT.

1
401 + a hint

No token? /mcp answers 401 with a resource_metadata pointer.

2
Discover

/.well-known/oauth-protected-resource (RFC 9728) → issuer + scopes.

3
Register

Dynamic Client Registration (or CIMD) creates the agent's client in Auth0.

4
Log in + consent

The customer signs in on a domain-level connection and approves bookings:*.

5
JWT issued

RFC 9068 access token: aud = /mcp, sub = the customer.

6
Verified call

verifyAccessToken passes → queries run WHERE user_sub = sub.

OAuth 2.1

Authorization code + PKCE for agents — no static API keys to leak.

RFC 9728

Protected Resource Metadata tells clients which authorization server guards /mcp.

RFC 9068

JWT access-token profile: verifiable iss, aud, exp and scope.

DCR + domain level

Agents self-register; domain-level connections let them log customers in.

The pro tip everyone misses
Default permissions for third-party apps
UnauthorizedAuthorized
☑ bookings:read☑ bookings:write

On the API's Access Policies, flip it to Authorized with both scopes checked. Now DCR clients can request bookings scopes — and the customer still approves them on the consent screen.
