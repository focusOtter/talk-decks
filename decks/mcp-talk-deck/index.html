The problem

Your MCP server is a public URL. Agents are knocking.

WHO

Which user?

A real person signed in — not a shared API key.

VIA

Which agent?

Cursor, Claude, Grok Bot… the client acting for them.

WHAT

Which tools?

Only the scopes the user agreed to.

OAuth already answers all three. Auth0 does the heavy lifting.

An MCP server is just an API with a very chatty audience. You need three answers: who's the user, which agent is acting, and what is it allowed to do. Good news: that's exactly what OAuth was built for — and the MCP spec uses it.
How it works

MCP server = OAuth resource server

  1. 1Client calls /mcp with no token → 401 + resource_metadata
  2. 2Server's RFC 9728 metadata points at your Auth0 tenant
  3. 3Client discovers Auth0 and registers itself
  4. 4User logs in + consents; token aud = your MCP URL
  5. 5Server validates the JWT (JWKS, issuer, audience) and runs the tool

CIMD

Client ID Metadata Document

The client shows a public ID card at a URL.

  • One client, one entry — no app sprawl
  • Real name + logo on the consent screen
client_id = https://client.example/oauth/client.json

Either way: the client finds you, registers, the user consents. No custom code.

DCR: every client signs up for its own account — GA, works everywhere. CIMD: the client ID is a URL to a public JSON "ID card" — manual registration is GA, dynamic CIMD is early access. Tip: prefer CIMD where you can — no app sprawl, and the consent screen shows the client's real name and logo.
The code · Next.js

Four small pieces

// 1. Tell clients where to log in (RFC 9728)
// app/.well-known/oauth-protected-resource/route.ts
export const GET = () => Response.json({
  resource: MCP_URL, authorization_servers: [AUTH0_ISSUER],
});

// 2. No token? Answer with just the challenge
const challenge = () => new Response(null, { status: 401, headers: {
  "WWW-Authenticate": `Bearer resource_metadata="${PRM_URL}"` } });

// 3. Verify the JWT: signature (JWKS), issuer, audience
const { payload } = await jwtVerify(token, JWKS, {
  issuer: AUTH0_ISSUER, audience: MCP_URL });

// 4. Gate each tool on its scope
if (!authInfo?.scopes.includes("game:create"))
  return deny("Ask for game:create");
Illustrative TypeScript (Next.js App Router + jose + MCP TS SDK authInfo). 1) metadata route. 2) the 401 challenge — that's all a missing token needs. 3) jwtVerify with the tenant JWKS, issuer, and audience = your MCP URL. 4) per-tool scopes like tool:whoami and game:create, granted via an RBAC role (we call ours "MCP Tool User"). The booth question

“If I pass my token to my agent, how can I tell if the user did it — or the agent?”

Token at your MCP server · whoami 
{
  "sub": "google-oauth2|…",  // user
  "client_id": "tpc_…",       // agent
  "aud": "https://focus-mcp-auth0
          .vercel.app/mcp",
  "scope": "tool:whoami"
}
After On-Behalf-Of exchange · RFC 8693 
{
  "sub": "google-oauth2|…",
  "aud": "https://api.example.com",
  "azp": "mcp_server_client",
  "act": { "sub": "mcp_server_client",
    "act": { "sub": "tpc_…" } }
}
sub = whoclient_id / azp = via whatact = the whole chain3rd-party APIs? Token Vault
Answer: it's already in the token. sub = the user. client_id (azp in some token profiles) = the acting client — here tpc_…, a dynamically registered Cursor / Grok Bot client. aud = our MCP URL, scope = tool:whoami. When your MCP server calls a downstream API for the user, Auth0's On-Behalf-Of token exchange (RFC 8693) adds an act claim naming each actor, so the chain is explicit. For third-party APIs like GitHub or Google, Token Vault holds and refreshes those tokens.
Getting started

Do this and it just works

  • No token? Reply 401 + resource_metadata. That's it.
  • API identifier = your production MCP URL
  • Promote login connections to domain level for third-party clients
  • Set a default third-party client grant
  • Write scope descriptions for humans + turn on use_scope_descriptions_for_consent
  • Prefer CIMD to skip client sprawl

Apps per tenant: Free 10 · self-service paid 100

Checklist from building the spike — each one is a single setting. Before/after: raw scope name on consent vs. a human description ("See who you're signed in as") once use_scope_descriptions_for_consent is on. Free plan allows 10 apps, self-service paid plans 100 — another reason CIMD is nice.
